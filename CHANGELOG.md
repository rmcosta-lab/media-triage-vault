The table's data source is Phase 19's `GET /api/scans/{id}/report` (already joins media/metadata/classification into one array), avoiding an N+1 per-file fetch; group/confidence/errors/country filters run client-side over that array before handing rows to the table. Each row shows a live thumbnail (`GET /api/files/{id}/thumbnail`, Phase 17); clicking a row opens a detail panel with the file's classification reasons and device/capture metadata, all already present in the fetched row. The detail panel's routing-group `<select>` is the manual-override editor — closes the last unbuilt route from README §25's "Classificação" group: `PATCH /api/files/{file_id}/classification`, added to the backend this phase (mirrors the CLI's Phase 12 `override` command exactly: validates against `ROUTING_GROUPS`, requires an existing `Classification` row, writes only `manual_routing_group`/`effective_routing_group`/`override_timestamp`). Manually verified in a real browser via `playwright-cli`: scanned and classified 4 fixtures across 4 routing groups, exercised every filter, overrode a file's group, watched the row pick up a "manual" badge, then reloaded the page and confirmed the override was still there — proving it round-tripped through the backend rather than only updating local state. `@tanstack/react-table` turned out to be on major version 9, a hard API break from the commonly-known v8 (`useReactTable`/`getCoreRowModel`/`flexRender`) — the installed package bundles its own agent-oriented `skills/*.md` docs (mirroring the Next.js `AGENTS.md`/`CLAUDE.md` pattern from Phase 20), which were read to implement the table against `useTable`/`tableFeatures`/`createColumnHelper`/`table.FlexRender` correctly. Also fixed a real `eslint-plugin-react-hooks` `set-state-in-effect` finding by moving the review page's data-fetch-on-mount to the documented cancellation-guarded `.then()`/`.catch()` pattern instead of an early synchronous `setState` inside the effect body.
- Phase 20 — Frontend scaffold + dashboard: `frontend/` — Next.js (App Router) + TypeScript + pnpm, opening Stage G. `frontend/lib/api.ts` is a typed client with Zod schemas mirroring the Phase 17-19 response shapes, parsed at every fetch call site; `app/page.tsx` (a single client component) drives a scan-launch form (path + recursive, validated by the backend's own `400` rather than client-side) through a live SSE progress panel (browser-native `EventSource` against `GET /api/jobs/{id}/events`), a scan summary, a Classify trigger reusing the same watch pattern, and a group-totals dashboard from `GET /api/scans/{id}/report`. Manually verified the entire flow in a real Chromium browser (`playwright-cli`): filling a path, watching live progress update the DOM with no reload, seeing group totals render correctly for two real fixtures, and the invalid-path error path showing the backend's exact message. That same manual pass caught a real bug fixed in this phase: the browser blocks `fetch`/`EventSource` from `localhost:3000` to `127.0.0.1:8000` as cross-origin, so `backend/app/api/app.py` gained `CORSMiddleware` scoped to `localhost`/`127.0.0.1` on any port (`allow_origin_regex`, never a non-loopback origin) — a code-review pass alone would not have caught this, since every backend unit/integration test uses `TestClient` directly and never exercises actual browser CORS enforcement. Removed `next/font/google` from the scaffold to avoid a build-time fetch to Google's font CDN, keeping the existing system-font stack instead.
- Phase 19 — Plan/execute API: the backend's HTTP surface closes the full US-001→US-004 loop — `PUT /api/scans/{id}/destinations`, `POST /api/scans/{id}/move-plan`, `GET /api/move-plans/{id}`, `POST /api/move-plans/{id}/approve`, `POST /api/move-plans/{id}/execute`, `GET /api/move-runs/{id}`/`.../cancel`/`.../report`, and `GET /api/scans/{id}/report`. `execute` is a new `job_type="execute"` on Phase 18's job runner — its `Job.id` doubles as README §25's "move run" id rather than inventing a second entity, since the data model never defines a separate `MoveRun` table. The API enforces "nothing moves without confirmation" structurally: `execute` returns `400` unless `MovePlan.approved_at` (a Phase 14 field, unused until now) is set, closing the gap the CLI only closed with a `--confirm` flag. Refactored `services/move_report.py` and the new `services/reports.py::build_report_payload` to derive their JSON purely from persisted rows instead of a live "just ran this" summary object — the same builder now serves both the CLI's file-writing commands (Phase 13/16, unchanged behavior, existing tests pass as-is) and the API's on-demand report reads, with zero duplicated computation. Manually verified the complete flow with `curl` against two real fixtures: scan → classify → destinations → move-plan (dry run — nothing on disk) → execute-before-approve (`400`) → approve → execute (`202`) → both files verified moved on disk by content, source directory left empty.
- Phase 18 — Jobs + progress: the API can now trigger work instead of only reading it. `POST /api/scans` and `POST /api/scans/{scan_id}/classify` queue a background job and return `202` immediately with a `Job`; `GET /api/jobs/{job_id}` polls it and `GET /api/jobs/{job_id}/events` streams it live over Server-Sent Events until it reaches a terminal state; `POST /api/scans/{scan_id}/cancel` requests cancellation. `backend/app/services/job_runner.py` is a single daemon worker thread draining a `queue.Queue[tuple[Engine, int]]` one job at a time (README §26 — no Celery/Redis, limited concurrency), persisting all state in a new `Job` SQLite row rather than in memory; the engine travels with each queued item (not a hardcoded default) specifically so the worker always talks to whichever database the submitting request used — otherwise test isolation would silently break, since Phase 17's session dependency opens a fresh `Engine` per request. `should_cancel` hooks were added to the four services a job can drive — `scan_folder` (checked after each flushed batch), `detect_media_types_for_scan` (before each row), `extract_metadata_for_scan` (before each batch), `classify_scan` (before each file) — all default `None` so no existing CLI behavior changes; cancellation is only ever honored at these existing per-item boundaries, never mid-file. `scan_folder` also gained an `on_scan_created` callback so a scan job's `Job.scan_id` is known within milliseconds of starting rather than only once the whole scan finishes — otherwise a client would have nothing to poll or cancel by for a large scan's entire duration. A job that raises is caught and marked `status="failed"` without killing the worker thread. Manually verified end to end against a real `media-organizer serve` run: `curl -N .../jobs/{id}/events` streamed a scan job to completion, `netstat` confirmed the process only ever listened on `127.0.0.1`.
- Phase 17 — FastAPI read layer: `media-organizer serve [--port 8000]` starts a local, read-only FastAPI app (`backend/app/api/`) opening Stage F — the first phase to expose anything over HTTP, and the last one before Next.js has something to read from. Five GET routes serve what the CLI has already produced: `/api/scans/{id}`, `/api/scans/{id}/files` (paginated), `/api/files/{id}/classification`, `/api/files/{id}/metadata`, `/api/files/{id}/thumbnail` (generated on first request via Phase 13's `generate_thumbnail`, cached under `runtime/thumbnails/api/{id}.jpg` thereafter). Every response goes through an explicit Pydantic read schema rather than a raw model dump, both to keep `absolute_path` off the wire and — same exclusion the CLI's `inventory.json` already applies (README §14.4/§28) — to keep `gps_latitude`/`gps_longitude`/`gps_position_raw`/`location_information` out of `ClassificationRead`/`MediaMetadataRead` entirely. `serve` hardcodes `host="127.0.0.1"` with no `--host` flag at all, by design (mission principle 1). The default Swagger/ReDoc docs are disabled (`docs_url=None`/`redoc_url=None`) since they'd otherwise fetch their JS/CSS from a CDN — a direct violation of the same "no CDN assets" principle — while `/openapi.json` stays on since it's generated in-process with no network activity. Manually verified the server only binds `127.0.0.1` via `netstat` while running. Added `fastapi`/`uvicorn[standard]` as runtime dependencies and `httpx` as a dev dependency (required by `fastapi.testclient.TestClient`); added `fastapi.Depends` to ruff's B008 allowlist alongside the existing Typer entries, since FastAPI's own documented pattern is `= Depends(...)` as a parameter default.
- Phase 16 — Execute/resume CLI + move report: `media-organizer execute --scan-id <id> --output <dir> [--confirm]` closes Stage E and US-004 — the last CLI phase before FastAPI. Without `--confirm` it only prints the README §16 Etapa 6 confirmation summary (files to move, bytes, blocked count, already-finished count from a prior run) and touches nothing; with `--confirm` it calls Phase 15's `execute_move_plan` against the scan's latest `MovePlan`, prints per-file progress, and installs a `SIGINT` handler that sets a flag instead of raising `KeyboardInterrupt` — cancellation is only honored between files (checked by the executor's existing per-operation loop boundary), never mid-copy or mid-rename. Resume has no separate command: re-running `execute --confirm` on the same scan resolves the same plan and calls the already-idempotent executor again, which is exactly what a kill-and-resume test exercises (`should_cancel` forced after the first file to simulate an interrupted run, then a second CLI call finishes the rest without redoing the first). New `backend/app/services/move_report.py` writes `move_report.json` (full per-operation detail plus totals/`by_error_code`, README §19.3) and `move_report.csv` after every execution. Also added a `should_cancel`-stops-the-loop test to Phase 15's `test_move_executor.py`, since this phase is the first to actually exercise that hook. Manually verified end to end against `backend/tests/fixtures/`: 8/8 files completed, source directory left empty, correct byte totals in the report. Interactive Ctrl+C behavior isn't scriptable cross-platform in an automated test and is left as a manual check.
- Phase 15 — Transactional executor: `backend/app/services/move_executor.py`'s `execute_move_plan` drives every `MoveOperation` still `planned` on a Phase 14 move plan through to `completed`/`failed`, closing Stage E's core safety layer (README §17/§18). Same-volume files go through an atomic `os.rename`; cross-volume files follow the README §17.3 sequence — hash the source, stream-copy into a `name.partial-<operation-id>` temp file next to the real destination, `flush`+`fsync`, verify size then hash, rename the temp file onto the final destination, then delete the source, confirming it's actually gone. `standard` validation mode only requires a hash for the cross-volume case (same-volume rename is size-checked); `strict` hashes every operation. The rename-vs-copy choice runs through one `core/volume.py::is_same_volume(a, b)` helper (`os.stat().st_dev` equality via each path's nearest existing ancestor) — no call site inspects a drive letter or mount point. Every operation re-checks `SOURCE_MISSING`/`SOURCE_CHANGED` at execution time (not just trusting the plan) and re-validates that the destination hasn't appeared since planning (`DESTINATION_EXISTS`), rather than ever overwriting. The journal is consulted before every operation: a `completed` row is never redone, and a row a crashed run left mid-flight (`validating`/`copying`/`verifying`/`renaming`/`deleting_source`) is reconciled by `_resume_or_reset` — completed in place if the destination file already matches the expected size, otherwise its stray `.partial-*` file is cleaned up and the row restarts from `planned`. `MOVE_OPERATION_STATUSES` (`models/move_plan.py`) now carries the full README §18 state list Phase 14 left for this phase to add. Covered by temp-dir tests for a same-volume rename, a simulated cross-volume copy (`is_same_volume` monkeypatched, since a single test filesystem has no real second volume), a mid-copy failure, a hash mismatch, a destination that appears between planning and execution, an idempotent re-run, and both crash-resume shapes. CLI wiring, confirmation, live progress, cancellation, and the move report are Phase 16.
- Phase 14 — Destinations + move plan (dry run): `media-organizer destinations --scan-id <id> --config <file.json>` maps each routing group to a destination folder (`DestinationRule`, README §24.4, unique per `scan_id`+`routing_group`, replaced wholesale on every call) and `media-organizer plan --scan-id <id>` generates a dry-run move plan (`MovePlan`+`MoveOperation`, README §24.5/§24.6 — the same journal table Phase 15's executor will extend with execution states, this phase only ever writing `planned`/`blocked`) — closing Stage E's opening phase and US-003. `backend/app/services/move_plan.py` computes a flat `destination_root/[sanitized country subfolder]/original_file_name` path per classified, mapped file and runs every README §16 Etapa 5 validation before persisting: source missing, source changed since scan, source locked (best-effort, via a probing open), source equals destination, path exceeding the 260-character Windows limit, a duplicate destination within the same plan, a name collision against an existing file (inherently case-insensitive — `Foto.jpg`/`foto.jpg` collide, README §17.5/tech-stack "Cross-platform"), insufficient free space per destination volume, and a non-writable destination — the first failing check blocks the file with an `error_code`, everything else is left `planned`. Nothing under the source root is ever touched beyond a `stat`/probing `open`, and no destination directory is ever created — verified both by a dedicated "never writes" unit test and a manual run against the real fixtures directory. New `backend/app/core/destination_paths.py` holds the pure helpers (`sanitize_path_component`, `exceeds_windows_path_limit`, `paths_collide`). Caught two real bugs while testing: `DestinationRuleRepository.replace_for_scan` was inserting replacement rows before flushing the deletes of the old ones, tripping the `(scan_id, routing_group)` unique constraint on a second `destinations` call (SQLAlchemy's default flush order runs inserts before deletes); and `_source_changed`'s datetime comparison always reported "changed" because SQLite round-trips `datetime` as naive while a freshly-`stat`-ed value was timezone-aware, so every file would have been spuriously blocked.
- Phase 13 — Thumbnails + static reports: `media-organizer report --scan-id <id> --output <dir>` (README §43/§19) closes Stage D — `backend/app/services/thumbnails.py` generates a JPEG preview per file dispatched by media kind (Pillow for standard raster images, `pillow-heif` for HEIC/HEIF, `rawpy` — embedded-preview `extract_thumb()` first, full `postprocess()` decode as fallback — for RAW/DNG, an FFmpeg frame grab via the Phase 2 `run_tool` resolver for video), catching every decode failure per file so one corrupt or unsupported file never aborts the batch; `backend/app/services/reports.py` joins `MediaFile`+`MediaMetadata`+`Classification` per file and writes `report.json`/`report.csv`/`report.html` (self-contained Jinja2 template with inline CSS/JS group/confidence/error/country filters, no CDN, per README §19.4) plus a regenerated `errors.log` into one `--output` directory, reusing Phase 7's coordinate-exclusion and error-log helpers so coordinates never reach the report (README §14.4/§28). Fixed an FFmpeg frame-grab bug along the way: newer FFmpeg's `image2` muxer silently writes nothing for a single-filename target unless `-update 1` is passed. RAW/DNG thumbnailing has no real fixture to test against — same gap Phase 9 hit for `IPhoneRawRule` — so it's covered by a monkeypatched `rawpy` success case and a real-file `LibRawError` failure case instead. Added `rawpy`/`Jinja2` to `pyproject.toml` (both already pinned in `specs/tech-stack.md`); mypy strict required importing rawpy's enum/exception types from `rawpy._rawpy` directly, since rawpy's own `__init__.py` only re-exports them under `TYPE_CHECKING`.
- Phase 12 — Classify CLI + overrides: `media-organizer classify --scan-id <id>` (`backend/app/services/classification.py`, README §38/US-002) wires Phases 8-11 together — runs all five Phase 9/10 rules against each file's raw ExifTool tag dict (`MediaMetadata.raw_json`), resolves the winning routing group via Phase 8's priority resolver, resolves GPS to a country via Phase 11, and persists one `Classification` row per file, printing each file's routing group, confidence, and reasons as it goes. Screenshot's own README §13.4 confidence bands are honored at assembly time (`review_threshold=0.85` when the winner is `mobile_screenshot`, the shared `0.60` default otherwise) — the assembly-time policy Phase 8 anticipated but left for this phase's orchestrator to apply. Re-running `classify` updates the automatic fields without touching an existing manual override. `media-organizer override <media_file_id> <routing_group>` records a manual correction (`manual_routing_group`/`effective_routing_group`/`override_timestamp`, README §15.3 — the last column deferred from Phase 8), validated against Phase 8's `ROUTING_GROUPS` and requiring a prior `classify` run. Formalized `routing_group: str` onto the `ClassificationRule` protocol (`rules/engine.py`) now that an orchestrator actually needs it structurally, rather than relying on the informal per-rule convention Phase 9/10 established.
- Phase 11 — Offline country resolution: `backend/app/services/country.py` resolves GPS coordinates to a country fully offline (README §14) — `extract_coordinates` reads ExifTool's normalized `GPSLatitude`/`GPSLongitude` first, falling back to parsing an ISO 6709 `LocationInformation` string for video containers that only carry that atom; `CountryResolver` loads a bundled `backend/data/geography/countries.geojson` (Natural Earth 1:110m Admin-0 Countries, trimmed from 839 KB to 192 KB by dropping ~166 unused columns and rounding coordinates to 3 decimals) into a Shapely `STRtree` and resolves via point-in-polygon; no GPS, invalid coordinates, or an ocean point all resolve to `country_code="unknown"`; a point within ~5.5 km of its country's polygon boundary is flagged `method="point_in_polygon_near_border"` with reduced confidence per README §14.5. Also fixed `inventory.json` (Phase 7) to stop exporting raw `gps_latitude`/`gps_longitude`/`gps_position_raw`/`location_information` by default, closing README §14.4/§28's "never show coordinates in default output" requirement that postdated Phase 7's original scope.
- Phase 10 — WhatsApp + screenshot rules: `WhatsAppRule` (`backend/app/rules/whatsapp.py`, README §12) scores the four §12.1 filename patterns at `0.65` and a `WhatsApp`-containing directory segment at `0.45`, adds a `+0.10` absent-camera-metadata bonus only on top of one of those (never alone — §12.3/§12.4's explicit "absent metadata alone: don't classify"), caps at `1.00`, and flips the label to `whatsapp_sent` on a `Sent` directory segment. `ScreenshotRule` (`backend/app/rules/screenshot.py`, README §13) scores a name-pattern match at `0.90` (clears the `>=0.85` auto-classify band, §13.4) and otherwise sums four weighted medium signals (PNG/HEIF format, absent camera metadata, vertical orientation, phone-compatible aspect ratio), explicitly refusing to classify from geometry signals alone even if their weighted sum would otherwise cross the floor (§13.3's safety rule, enforced as a direct check rather than left as an emergent property of the weights) and refusing anything under the `0.60` classification floor. Both rules stay pure `(media, metadata) -> RuleResult` functions per the Phase 8 contract, unit-tested straight from README's worked cases; a dedicated test threads a screenshot result through `build_classification_result` to demonstrate the full three-band `requires_review` behavior end to end.
- Phase 9 — Video + iPhone + RAW rules: three concrete `ClassificationRule`s against the Phase 8 contract, each unit-tested straight from README's own worked cases. `VideoRule` (`backend/app/rules/video.py`, README §9) reads the MIME/`FileType`/`media_kind` signals Phases 5-6 already combined rather than re-invoking FFprobe. `IPhoneRule` and `IPhoneRawRule` (`backend/app/rules/iphone.py`, README §10-11) score `Make=Apple`+`Model` starting with `iPhone` at `0.98` (matching README §15's own example verbatim), fall back to a tiered score from secondary QuickTime-adjacent signals (`Software`, `Encoder`, `HandlerDescription`, ISO-6709-shaped `LocationInformation`) for videos with no direct Make/Model, and never treat a filename pattern alone as a positive signal (README §10.3/§10.4) — an all-metadata-absent `IMG_1234.JPG` scores `0.0`, safely under the spec's `<=0.40` cap. `IPhoneRawRule` independently re-checks Make/Model rather than depending on `IPhoneRule`'s output (the protocol gives rules no cross-rule channel) and fires only for DNG + Apple/iPhone; a non-Apple DNG scores `0.0`, which — combined with the Phase 8 resolver falling back to `other` when no candidate claims a group — reproduces the roadmap's "non-Apple DNG routes to other" without a rule ever asserting it directly.
- Phase 8 — Rule engine core: `backend/app/rules/engine.py` defines the shared classification contract ahead of any concrete rule — `RuleResult` (label/score/reasons, README §15), the `ClassificationRule` protocol, `ClassificationResult`, and `resolve_routing_group`, a pure priority lookup over the six routing groups (`video > mobile_screenshot > whatsapp_received > iphone_raw > iphone_photo > other`, README §5.1) that picks a winner among whichever groups a rule actually nominated; `build_classification_result` assembles the final result with a shared `DEFAULT_REVIEW_THRESHOLD=0.60` gating `requires_review`. New `Classification` table (README §24.3, `backend/app/models/classification.py`) with the `automatic_`/`manual_`/`effective_routing_group` split ready for Phase 12's overrides. Unit-tested entirely against synthetic `RuleResult` data per the roadmap's done criterion — no concrete rule exists yet (Phase 9/10).
- Phase 7 — Scan CLI: `media-organizer scan <path> --recursive --output <dir>` (Typer, `backend/app/cli/main.py`, installed as a `project.scripts` entry point) wires the Phase 4-6 engine end to end — scan, media-type detection, batch metadata extraction — over one SQLite session, printing progress per batch and writing `errors.log`/`inventory.json` (nested per-file metadata, README §37/US-001) to `--output`; a hidden `--database` override keeps tests off the real database. Fixed a Typer default behavior where an app with a single `@app.command()` collapses to a bare single-command CLI, dropping the `scan` subcommand name, by adding an explicit `@app.callback()`.
- Phase 6 — Batch metadata extraction: `backend/app/services/metadata.py` extracts the README §8.2 field set for a scan's pending rows with one batched ExifTool process (`-j -n`, explicit `-TagName` args) per `DEFAULT_BATCH_SIZE=200` chunk — never one process per file — and normalizes the result onto a new one-to-one `MediaMetadata` table (`backend/app/models/media_metadata.py`: capture datetime resolved from `DateTimeOriginal`/`CreateDate`/`MediaCreateDate`/`TrackCreateDate`, GPS, camera, and audio/video technical fields, plus a `raw_json` subset for audit); `MediaFile.file_type`/`mime_type`/`width`/`height`/`duration_seconds` are refreshed from ExifTool when present; every `media_kind="video"` row is validated with FFprobe and marked `processing_status="error"`, `error_code="VIDEO_UNREADABLE"` per README §9 when no decodable video stream is found; new `corrupt_video.mp4` fixture (a truncated MP4) exercises that path.
- Phase 5 — Media type detection: `backend/app/services/media_type.py` combines a fixed extension→category/MIME table (`backend/app/core/media_signatures.py`, README §6.1–§6.3, deliberately not `stdlib mimetypes`/the OS registry) with a magic-byte file-signature sniffer (JPEG, PNG, GIF, BMP, WEBP, TIFF-based RAW, Fujifilm RAF, HEIC/HEIF and MP4/MOV `ftyp` boxes, AVI `RIFF`, MKV/WEBM `EBML`) into a `media_kind` (`image`/`video`/`unsupported`) and an `extension_mismatch` flag on `MediaFile`; `detect_media_types_for_scan` runs detection over an existing scan's pending rows and records read errors without aborting; new `misnamed_video_as_jpg.jpg` fixture exercises the roadmap's misnamed-file done criterion.
- Phase 4 — Scanner: recursive `pathlib` walk (`backend/app/services/scanner.py`) with cross-platform ignore patterns (`Thumbs.db`, `desktop.ini`, `*.tmp`, `.DS_Store`, `._*` AppleDouble sidecars, `.Spotlight-V100`, `.Trashes`, `.fseventsd`) in `backend/app/core/ignore_patterns.py`, no symlink following, batched persistence with a progress callback, NFC-normalized path storage via `backend/app/core/paths.py`, and per-entry access errors recorded without aborting the scan; unit and integration tests including an unreadable entry, an AppleDouble sidecar, and an NFD/NFC filename pair.
- Phase 3 — Data model + SQLite: `Scan` and `MediaFile` SQLModel tables (README §24.1/§24.2) with a foreign-key relationship; SQLite engine/session module resolving `runtime/database/media_organizer.db` relative to the repo root; generic `Repository[T]` CRUD layer with `ScanRepository`/`MediaFileRepository`; round-trip and CRUD tests against a real SQLite engine.
- Phase 2 — Tooling + fixtures: vendored ExifTool (Windows) under `tools/exiftool/windows-x64/` behind a single per-platform resolver in `backend/app/core/tools.py`; FFmpeg/FFprobe resolved from the system PATH for now instead of vendored, to avoid committing a ~100-250MB binary to git history (see `specs/tech-stack.md` "Bundled binaries"); added the first six test fixtures (iPhone JPEG w/ GPS, HEIC, WhatsApp-named file, screenshot-named PNG, small MP4, JPEG without EXIF) and a smoke test proving both tools run through the resolver.
- Phase 1 — Repo bootstrap: `pyproject.toml` pinned to Python 3.13 and managed with `uv`, ruff/mypy/pytest/pre-commit wired together, minimal `backend/app/` package skeleton, and one trivial passing test.
